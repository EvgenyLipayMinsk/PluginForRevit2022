# Маркировка, диагностика и отчёты MCP

Диагностические инструменты из таблицы зарегистрированы в `McpCommandExecutor` и `McpServer/tools.json`. Команды вызываются в UI-потоке Revit. Проверки не изменяют модель; операции записи статусов и файлов требуют явного `dryRun=false`. Скриншот необязателен.

| Команда | Результат |
|---|---|
| `check_cable_routes` | Связность размеченных линий по графу CableWalk, компоненты, недостижимые устройства/трассы, координаты концов и развилок. |
| `explain_cable_length` | Объяснение одной строки текущего КЖ: исходная длина, коэффициент, округление, резерв, итог и путь по рёбрам графа с ID исходных трасс. |
| `manage_clash_report` | Режимы `list`, `update`, `export`: чтение отчёта, статус/комментарий/опциональная картинка, Excel. |
| `capture_clash_view` | PNG текущего или указанного графического вида Revit: отдельный файл и/или скриншот выбранной коллизии. |
| `compare_clash_reports` | Новые, исчезнувшие и повторяющиеся коллизии двух наборов отчётов, изменения статусов и неоднозначности. |
| `check_line_consistency` | Нумерация, дубли, ёмкость, комментарии, приборы АПС и существующая проверка уровней/привязки устройств к трассам. |
| `compare_journal_with_model` | Сравнение А3 «Полный КЖ» с новым расчётом по модели: концы, марки кабеля, длины, суммы и распределение способов прокладки. |
| `run_project_checks` | Выбранные проверки вместе, отдельные результаты/ошибки, опциональная выгрузка JSON/XLSX с ID элементов. |

## Ручная маркировка

### Для пользователя Revit

1. В разделе «Маркировка» нажмите «Маркировка». Укажите систему, прибор и линию, выберите «Вручную, выбором устройств». В «Настройках маркировки» проверьте, что семейства отмечены для нужной системы, у них задано БЦО и выбран параметр этажа.
2. Нажмите «Далее: выбрать устройства» и укажите прибор. Для СОУЭ выберите стойку и номер прибора в ней, если номеров несколько.
3. Добавляйте устройства штатными кликами, Ctrl и рамкой. Вкладки видов переключаются в Revit. Список сохраняется между этажами. Для точной последовательности используйте «Точные клики» и Esc для завершения набора на текущем виде. Группы из рамки можно переставить в разделе «Устройства и порядок».
4. Нажмите «Промаркировать выбранное». Окно покажет количество записанных устройств. Если меняются параметры прибора, у устройств уже есть маркировка или есть предупреждения, проверьте предпросмотр и подтвердите запись. При ошибке очередь сохраняется.

### Для ИИ через MCP

Откройте исходный проект и включите MCP в Revit. Вызовите `get_project_info {}`, чтобы сверить активный документ. Получите ID через `filter_elements` или `get_parameter_values`. Согласуйте устройства и их порядок с проектировщиком. MCP получает готовый список ID.

Передайте в `mark_devices` следующие аргументы.

| Аргумент | Обязательность | Формат |
|---|---|---|
| `ids` | Да | Массив строк с ID устройств в согласованном порядке, в том числе с разных этажей. |
| `system` | Да | `aps`, `security` или `souye`. |
| `controller`, `line` | Да | Номера строками. Для СОУЭ номер прибора берётся из `ARBM_Номер прибора` выбранной стойки, линия от `1` до `20`. |
| `controllerElementId` | Для СОУЭ и `order:"route"`. Для остальных рекомендуется. | Целочисленный ID прибора или стойки. |
| `building` | Для АПС и СОУЭ в режиме разных корпусов. | Корпус, например `M2`. В режиме функциональных зон СОУЭ зону можно оставить пустой. |
| `comments` | Для АПС. | Точное значение «Комментарии» линии. В СОУЭ при пустом поле используется комментарий стойки или `СОУЭ`. |
| `order` | По умолчанию `manual`. | `manual` использует порядок `ids`. `route` вычисляет порядок по трассе. |
| `startNumber`, `dryRun` | По умолчанию `1`, `true`. | Первый номер целым числом. `dryRun:true` проверяет маркировку, `dryRun:false` записывает. |

Пример для АПС.

```json
{"ids":["501","507","504"],"system":"aps","controller":"1","line":"2","controllerElementId":420,"building":"M2","comments":"АПС","order":"manual","dryRun":true}
```

Проверьте `devices`, `failures`, `warnings` и `controller.changes`. При пустом `failures` покажите проектировщику порядок и предупреждения. После подтверждения повторите вызов с теми же аргументами и `dryRun:false`. Успех отмечается `applied:true`. Проверьте параметры устройств и прибора через `get_parameter_values`. Если ответ записи потерялся, перед повтором перечитайте эти параметры в модели.

## Межэтажные переходы

### Для пользователя Revit

Для нумерации по кабелю выберите «Автоматически по трассам журнала» и подготовьте трассы и переходы линии.

| Параметр или условие | Где задать | Допустимое значение или формат |
|---|---|---|
| Семейство перехода | На каждом этаже, через который проходит шахта | Точечный экземпляр `ARBM_Межэтажный переход` в категории «Оборудование». |
| Этаж | На трассе и переходе | Однозначный этаж в параметре, выбранном в «Настройках маркировки». |
| «Комментарии» | На трассе и переходе | Одинаковое значение нужной системы или линии. |
| Положение | На смежных этажах | Поставьте точки одной шахты друг над другом рядом с трассой, соблюдая непрерывность между этажами. |

При сообщении об ошибке проверьте указанные ID, этажи, «Комментарии», кабель у каждого конца и расположение соседних шахт. Перезапустите предпросмотр после поправок.

### Для ИИ через MCP

Для уже размеченной линии получите точный ключ через `list_marked_lines` и передайте его в `check_cable_routes` как строку `line`. При неоднозначном приборе укажите целочисленный `controllerElementId`. Для адресной линии СОТС или старой СОУЭ также передайте точное значение `routeGrouping` с трассы. Проверьте `devicesWithoutPath`, `diagnostics.unreachableRouteIds`, `diagnostics.transitionIds` и `diagnostics.transitionIssues`. Эти поля помогают найти места, которые проектировщику нужно проверить в модели.

Для предварительного расчёта нумерации ещё не размеченных устройств используйте `mark_devices` с `order:"route"`, `controllerElementId` и `dryRun:true`. Для проверки геометрической длины отдельной строки КЖ используйте `explain_cable_length`.

## Примеры

Получить ключи линий: `list_marked_lines {}`. Проверить выбранную линию:

```json
{"line":"aps|M2|1|1|АПС"}
```

Аргументы для `explain_cable_length`:

```json
{"system":"aps","comments":"АПС","recordNumber":1,"segmentLimit":200}
```

`recordNumber` — номер записи без заголовка, в порядке выгрузки «Полный КЖ». Для СОУЭ дополнительно требуется `parameterStandard: "eom"` или `"adsk"`. Этот выбор делает проектировщик. Для большой модели полный пересчёт может занимать минуты и блокировать Revit; перед вызовом сообщить об этом пользователю. Следующую часть пути получают через `nextSegmentOffset` → `segmentOffset`; каждый вызов пересчитывает журнал, кэша между вызовами нет.

`manage_clash_report`, сначала чтение:

```json
{"reportPaths":["D:\\Reports\\clashes.xml"],"action":"list","limit":100}
```

Предпросмотр изменения выбранного ключа:

```json
{"reportPaths":["D:\\Reports\\clashes.xml"],"action":"update","key":"KEY_FROM_LIST","status":"InWork","changes":{"comment":"Проверить обход лотка"}}
```

Для записи повторить с `dryRun:false`. `changes.comment:""` явно очищает комментарий; отсутствие поля сохраняет прежний текст. Опциональный `imagePath` добавляет/заменяет скрин, `removeScreenshot:true` убирает только пользовательский скрин. Открытый в плагине отчёт нужно переоткрыть, чтобы увидеть изменения его файлов. Режим `export` требует `savePath` с расширением `.xlsx`. Столбец скриншота находится после комментария (D) на обоих листах статусов.

Предпросмотр захвата текущего вида и привязки к коллизии:

```json
{"reportPaths":["D:\\Reports\\clashes.xml"],"key":"KEY_FROM_LIST"}
```

`capture_clash_view` не наводит камеру на коллизию: вид выбирается проектировщиком заранее или задаётся через `view`. Для отдельного PNG вместо отчёта указать `savePath`. Запись — только `dryRun:false`. Вид временно открывается через ViewSession, затем восстанавливается. Шаблоны и неграфические виды не экспортируются.

Сравнение отчётов:

```json
{"beforePaths":["D:\\Reports\\old.xml"],"afterPaths":["D:\\Reports\\new.xml"]}
```

Сопоставление идёт по однозначному ключу внутри проверки, затем по однозначной паре Revit ID и имён моделей. При нескольких конфликтах одной пары возвращается неоднозначность. Исчезнувшая коллизия автоматически не получает статус «Исправлено».

Сверка отредактированного КЖ:

```json
{"system":"aps","comments":"АПС","journalPath":"D:\\Reports\\journal.xlsx","lengthToleranceM":0.01}
```

Перед сравнением пересчитать и сохранить книгу в Excel: формулы читаются по сохранённым результатам. Поддерживается А3 «Полный КЖ»; старый шаблон AerBIM не поддерживается этой командой. Сопоставление по точным обозначениям начала/конца: переименование устройства выглядит как отсутствующая/лишняя строка. Дубли не сопоставляются наугад.

Все проверки с предпросмотром сохранения результата:

```json
{"checks":["parameters","routes","lines","warnings","health"],"savePath":"D:\\Reports\\checks.xlsx"}
```

Повтор с `dryRun:false` сохраняет файл. Допускаются `.json` и `.xlsx`. Флаг не разрешает исправлять модель: `run_project_checks` всегда только проверяет. Результаты ошибок отдельных проверок сохраняются вместе с остальными.

## Границы проверок

- Область новых проверок линий — семейства, включённые в линии в текущем профиле маркировки, с исключением приборов ARK из списка устройств. Проверка связности выполняется только для размеченных линий.
- CableWalk использует допуски маркировки: стык 100 мм, устройство 600 мм, прибор 3 м. Это отдельный граф от графа расчёта КЖ; выводы по связности и геометрические длины не смешиваются.
- АПС автоматически ищет прибор по БЦО ARK, номеру, корпусу и комментарию. При неоднозначности указать `line` и `controllerElementId`. Для адресных СОТС/СОУЭ дополнительно нужно точное `routeGrouping`, чтобы не объединить трассы разных линий.
- Концы и развилки сами по себе не считаются ошибками. Сообщения по межэтажным переходам содержат ID экземпляров.
- Блок `journalLevels` использует существующую проверку АПС всего проекта, даже если проверка нумерации ограничена `line/comments`; это явно указано в ответе.
- Геометрия в объяснении длины — точки расчётного графа в мм внутренних координат Revit. Служебные соединения имеют `routeElementId:null`; при fallback встречается мост или прямое расстояние. Фиксированная служебная длина не имеет геометрического пути.
- Проверки параметров только читают определения и привязки; ФОП и параметры автоматически не добавляются. `passed` не означает полную нормативную проверку проекта.

## Проверки и развёртывание

Собрать `Release R2022`, затем запустить:

```powershell
Tests\CableJournalForms\run-smoke.ps1
Tests\ClashScreenshots\run-smoke.ps1
Tests\McpDiagnostics\run-smoke.ps1
node Tests/McpDiagnostics/schema-smoke.mjs "D:/Visual Studio/PluginForRevit2022"
```

Последнюю команду запускать с корректно заключённым в кавычки путём репозитория. Тесты покрывают путь и ID рёбер, обратный маршрут, мост, регрессии форм КЖ и картинок, сравнение отчётов, режимы list/update/export, dryRun, защиту результатов, сравнение КЖ, сохранение ID в JSON/XLSX, соответствие схем обработчикам. Тесты файлов выполняются вне Revit и не заменяют испытания восьми инструментов на модели; захват вида и проверки модельных данных требуют запущенного Revit.

После установки новой сборки перезапустить Revit, затем переподключить MCP-клиент/сервер, чтобы обновился список инструментов. Для испытаний используются отдельные сборки Revit 2021–2024. В открытой модели остаётся ранее загруженная DLL до перезапуска.
