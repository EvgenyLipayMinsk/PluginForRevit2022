# Workflow разработки AerBIM

`AGENTS.md` задаёт автоматическое подключение ролей. Профили Codex хранятся в `.codex/agents/`, навыки AerBIM — в `.agents/skills/`. Основной чат ведёт диалог с проектировщиком и передаёт решения координатору.

| Этап | Кто выполняет | Что передать дальше |
| --- | --- | --- |
| Постановка | `aerbim-development-coordinator` | Краткая карточка задачи: рабочая копия, версия Revit, ручная и MCP-точки входа, исходные данные, проверяемые критерии приёмки. Для неоднозначной логики подключить `aerbim-manual-logic-partner` и `grill-me`, если он доступен. |
| Реализация | `aerbim-csharp-developer` | Изменённые файлы, выполненные проверки, сценарии для Revit. Указать базовый коммит и идентификатор снимка правок с учётом новых файлов, если изменения ещё не закоммичены. |
| Тестовая сборка | `aerbim-build-engineer` | Исходный снимок, конфигурация и версия Revit, результат сборки, полный путь и SHA-256 полученной DLL. Передать тестировщику артефакт этого прогона. |
| Интеграционная проверка | `aerbim-integration-tester` | Версия Revit, тестовая модель и идентифицированная DLL. По каждому критерию указать способ запуска, ожидаемый и фактический результаты, доказательство и статус: прошёл, дефект, заблокирован или не применим. |
| Инструкции | `aerbim-instructions-writer` | Для затронутого сценария подготовить краткие шаги для пользователя Revit и MCP-инструкцию для ИИ. Перед нужным этапом дать таблицу параметров или аргументов. Для внутренних изменений отметить, нужна ли правка инструкций. |
| Ручная приёмка | Координатор и пользователь | Координатор передаёт проверенную сборку и короткие шаги. Пользователь подтверждает результат или сообщает о дефекте. |
| Ревью и коммит | Координатор и `aerbim-plugin-reviewer` | После ручной приёмки проверить итоговый diff. После устранения блокирующих замечаний выполнить коммит, если он входит в поручение. Сообщить хеш и что проверено. |
| MSI | `aerbim-build-engineer` | По отдельной команде собрать через `Installer/build-installer.ps1`. Указать исходную ревизию, версию пакета и путь к MSI. |

При дефекте координатор передаёт разработчику шаги, ожидаемый и фактический результаты. После исправления сборщик выпускает новую DLL, тестировщик повторяет затронутые сценарии. Дефекты ручной приёмки и блокирующие замечания ревью возвращаются в тот же цикл. При блокировке среды фиксируй причину и выполняй доступные независимые проверки.

Для одной задачи разработчик, сборщик и тестировщик используют согласованный снимок исходников. Независимые задачи с одновременной записью можно вести в отдельных Git worktree. Экземпляр Revit и тестовую модель согласовывай отдельно. Для целевых проверок используй подходящие сценарии из `Tests/McpDiagnostics`, `Tests/CableJournalForms` или `Tests/ClashScreenshots`.

## Контрольные сценарии для workflow

1. Изменение команды Revit и MCP подключает все пять ролей по этапам. Ручная приёмка использует DLL, проверенную тестировщиком.
2. Вопрос о текущем поведении остаётся исследованием с применимыми навыками.
3. Запрос тестовой DLL даёт тестовую сборку. Запрос MSI отдельно запускает штатную упаковку.
